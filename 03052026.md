## 1. Unified Hourly Analytics Chart Was Blank

**Symptom:** The Hourly Trends chart on the Cross-Platform Analytics page showed almost nothing — only one data point was visible and the rest of the canvas was empty.

**Root Cause:** The `/api/analytics/trends` backend endpoint (Program.cs) only returned hourly buckets where data actually existed in `ad_metrics`. If the DB had only one row (e.g. May 03, 07 PM), Chart.js received a single point and rendered it as a dot against a blank canvas.

**Fix — `backend/Program.cs`:**
- Generated a complete hourly timeline (all N buckets for the requested window) upfront using `Enumerable.Range`
- Both `combined` and `split` modes now fill missing hours with `0` using a dictionary lookup
- Chart always shows a full continuous line across the requested 24h / 48h window

## 3. Facebook Reach Always Zero in `ad_metrics`

**Symptom:** All 103 Facebook rows in `ad_metrics` had `reach = 0`. Google Ads rows had real reach values.

**Root Cause:** Facebook's Insights API does **not** return `reach` when the request includes `breakdowns=hourly_stats_aggregated_by_advertiser_time_zone`. Reach is a unique-user count; it cannot be split by hour. Facebook returns `"0"` for the field, and `ParseLong` stored it as `0` for every row.

**Fix — `backend/Services/MetricsFetchService.cs` (`SyncAccountInsightsAsync`):**
- Added two extra API calls (no hourly breakdown, `time_increment=1`) to fetch **daily reach** per ad for `last_7d` and `today`
- Built a `dailyReachLookup` dictionary keyed on `(adId, dateStart)`
- Built `hourlyCountPerDay` to know how many hourly rows exist per `(adId, day)`
- In the hourly upsert loop: replaced `ParseLong(row, "reach")` with `dailyReach / hourCount` — distributes the daily total evenly across the day's hourly rows
- Result: Facebook rows now carry real proportional reach instead of 0

## 5. Google Ads Fetching Cumulative Daily Data Instead of Hourly

**Symptom:** The DB had only 7 Google Ads rows — one per day — instead of per-hour rows. Google Ads UI ("When and where ads showed") clearly shows hourly data.

**Root Cause (`backend/Services/GoogleAdsSyncService.cs`, `SyncMetricsAsync`):**
1. The GAQL query only selected `segments.date` — no `segments.hour`
2. Without `segments.hour`, the API returns one aggregated daily total per ad
3. The timestamp was stored as `date.Date` (always midnight), erasing any time component

**Fix:**
```sql
-- Before
SELECT ... segments.date FROM ad_group_ad WHERE segments.date DURING LAST_7_DAYS LIMIT 1000

-- After
SELECT ... segments.date, segments.hour FROM ad_group_ad WHERE segments.date DURING LAST_7_DAYS LIMIT 5000
```
- Read `segments.hour` from each row
- Built hourly timestamp: `date.Date.AddHours(hour)` (UTC)
- Increased LIMIT from 1000 → 5000 (7 days × 24 hrs × N ads needs more rows)
- Result: DB now stores one row per `(ad, date, hour)` matching Google's "Day & hour" report

## 7. Update Button Not Downloading Data + No Live Feedback

**Symptom:** Clicking the "Update" button on Platform Service appeared to do nothing — no data was added to the DB, and the screen showed stale status (IDLE) even while a sync was theoretically running.

### Bug A — Simulated metrics always skipped (Backend)

**Root Cause:**
- `GenerateSimulatedGoogleSync` checked `m.Date >= todayStart` (any row for the whole day)
- `FetchPlatformMetrics` (non-FB/non-Google platforms) checked `m.Date >= dayStart && m.Date < dayEnd`
- Since previous syncs already created rows for today, every subsequent Update generated **0 new rows**

**Fix — `backend/Services/GoogleAdsSyncService.cs`:**
```csharp
// Before: skips if any row exists for today
var todayStart = now.Date;
var alreadyFetched = await db.AdMetrics.AnyAsync(m => ... && m.Date >= todayStart, ct);

// After: skips only if this exact hour already has a row
var currentHour = DateTime.SpecifyKind(now.Date.AddHours(now.Hour), DateTimeKind.Utc);
var alreadyFetched = await db.AdMetrics.AnyAsync(m => ... && m.Date == currentHour, ct);
metric.Date = currentHour;
```

**Fix — `backend/Services/MetricsFetchService.cs` (`FetchPlatformMetrics`):**
- Same change: check for current hour bucket (`>= currentHour && < nextHour`) instead of whole day

### Bug B — No live feedback while syncing (Frontend)

**Root Cause:** `renderPlatformServiceScreen()` rendered once immediately after clicking Update (before the sync even started running). The screen never updated again, so the user saw `IDLE` even while the service was `FETCHING`, and never saw `SUCCEEDED`.

**Fix — `frontend/src/main.js`:**
- Added `_platformServicePollTimer` and `_stopPlatformServicePoll()` helper
- After initial render: if either service has `isRunning = true`, start a **4-second polling loop**
- Each poll tick silently patches the `Fetching/Idle` badge, `Last Run` timestamp, and `Outcome` pill using element IDs (no full re-render, preserves event listeners)
- When both services become idle: polling stops and triggers one final full re-render
- Added `_stopPlatformServicePoll()` call at the top of `switchScreen()` so polling cancels cleanly when navigating away
- Added `id` attributes to the running badge, outcome badge, and last-run span in `renderServiceCard`
